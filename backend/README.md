# Supplement Tracker — Backend

FastAPI + SQLAlchemy + PostgreSQL REST API for tracking supplement restock timing, with per-user accounts.

## Setup

### 1. Start Postgres (via Docker)

```bash
cd backend
docker compose up -d
```

### 2. Configure environment

```bash
cp .env.example .env
```

Generate a real `SECRET_KEY` (used to sign auth tokens) and put it in `.env`:

```bash
python3 -c "import secrets; print(secrets.token_hex(32))"
```

The `DATABASE_URL` default already matches `docker-compose.yml`, so no edit needed there for local dev.

### 3. Install dependencies

```bash
python3 -m venv venv
source venv/bin/activate        # on Windows: venv\Scripts\activate
pip install -r requirements.txt
```

### 4. Run migrations

```bash
alembic upgrade head
```

Whenever you change `models.py`:

```bash
alembic revision --autogenerate -m "describe your change"
alembic upgrade head
```

Always review autogenerated migrations before running them.

### 5. Run the API

```bash
uvicorn main:app --reload
```

- API: http://127.0.0.1:8000
- Interactive docs (Swagger UI): http://127.0.0.1:8000/docs — you can authenticate here too via the "Authorize" button

## Auth

Accounts are per-user; every supplement and source belongs to exactly one user and is invisible to everyone else.

- **Passwords** are hashed with `bcrypt` (via the `bcrypt` package directly — not `passlib`, which has a known incompatibility with modern bcrypt versions)
- **Tokens** are JWTs, signed with `SECRET_KEY`, valid for 7 days
- Every `/supplements*` and `/sources*` route requires `Authorization: Bearer <token>` and only ever touches the calling user's own data — attempting to access another user's supplement by ID returns a 404 (not a 403), so IDs can't be used to probe what exists

| Method | Path | Description |
|---|---|---|
| POST | `/auth/register` | Create an account (`email`, `password`) |
| POST | `/auth/login` | Log in (form-encoded `username`/`password` — OAuth2 convention), returns a JWT |
| GET | `/auth/me` | Get the current user (requires token) |

## Endpoints (all require auth)

| Method | Path | Description |
|---|---|---|
| GET | `/supplements` | List the current user's supplements |
| POST | `/supplements` | Create a new supplement (optionally with nested `sources`) |
| GET | `/supplements/{id}` | Get one supplement |
| PUT | `/supplements/{id}` | Partially update a supplement |
| DELETE | `/supplements/{id}` | Delete a supplement (cascades to its sources) |
| POST | `/supplements/{id}/restock` | Reset start_date to today (optionally pass `?new_total_doses=N`) |
| POST | `/supplements/{id}/sources` | Add a restock source |
| DELETE | `/sources/{id}` | Remove a restock source |

## File layout

- `database.py` — SQLAlchemy engine/session setup, reads `DATABASE_URL` from `.env`
- `auth.py` — password hashing, JWT creation/verification, `get_current_user` dependency
- `models.py` — ORM table definitions (`User`, `Supplement`, `Source`)
- `schemas.py` — Pydantic request/response contracts
- `crud.py` — DB read/write functions, all user-scoped where relevant
- `logic.py` — pure date-math (days_remaining, restock_date, status)
- `main.py` — FastAPI app and route handlers
- `alembic/` — schema migrations
- `docker-compose.yml` — local Postgres for development

## A note on production-readiness

This is a solid foundation, but a few things worth doing before deploying somewhere public:
- Rate-limit `/auth/login` and `/auth/register` to slow down brute-force/spam attempts
- Consider shorter-lived access tokens plus a refresh-token flow instead of a single 7-day token
- Add email verification if you want to be confident emails are real
